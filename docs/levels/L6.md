# L6 — Spec-driven + TDD: "specs define done"

Goal: every feature starts as an EARS spec with measurable acceptance criteria approved by a lead; tests are
committed red before any implementation and proven red for the right reason; implementation is a separate commit
that cannot touch tests; two numbers (criteria coverage, mutation score) say whether the tests mean anything.

## Rules

- **No spec, no code.** `specs/FEAT-xxx-<name>.md` from `specs/TEMPLATE.md`: tier, EARS requirements (`REQ-n`),
  at most 7 measurable criteria (`AC-n`), out of scope, unchanged behavior, lead-approval box. Adjectives such as
  fast/friendly/simple are banned unless a number and unit stand next to them.
- **Two roles, two agents.** `test-writer` writes tests from AC ids only (never implementation); `implementer`
  makes them green and never edits a test file. When a test and the spec disagree, the spec changes first in its
  own commit and the lead re-approves.
- **Red is proven, not assumed.** `scripts/verify-red.sh FEAT-xxx` checks out the commit before the tests, runs
  the test files on it, and passes only if every file loads, no test passes, and no failure is an import or
  compile error. CI runs it (`--auto`) for every `test(FEAT-xxx)` commit in the PR.
- **Commit convention.** `docs(FEAT-xxx):` spec · `chore(FEAT-xxx):` skeleton · `test(FEAT-xxx):` red ·
  `feat(FEAT-xxx):` green · optional `test(FEAT-xxx):` hardening. `scripts/ci/check-feat-commits.sh` rejects a
  `feat(` commit that touches `*.test.ts(x)` or `e2e/**`.
- **Numbers gate the merge.** `scripts/ci/check-ac-coverage.sh`: 100% of `AC-n` ids appear as test titles.
  Stryker on `src/lib` + `src/actions`: break below 70%.

## The feature flow

| Step     | Commit                 | Who / tool                                     | Must be true afterwards                                            |
| -------- | ---------------------- | ---------------------------------------------- | ------------------------------------------------------------------ |
| Spec     | `docs(FEAT-xxx): ...`  | human + lead                                   | status `approved`, lead box ticked, ≤ 7 ACs, no banned adjectives  |
| Skeleton | `chore(FEAT-xxx): ...` | `new-feature-slice` skill (+ `add-migration`)  | stubs throw `NotImplementedError`; `pnpm test` green (todos only)  |
| Red      | `test(FEAT-xxx): ...`  | `test-writer` agent / `write-spec-tests` skill | every AC has a test; `scripts/verify-red.sh` exits 0               |
| Green    | `feat(FEAT-xxx): ...`  | `implementer` agent                            | lint, types, unit, e2e green; mutation ≥ 70%; no test file touched |
| Harden   | `test(FEAT-xxx): ...`  | `test-writer`                                  | optional: kills survivors reported by Stryker                      |
| PR       | template               | human                                          | Plan section, reviewer agent, one human approval, CI green         |

### Why the skeleton commit exists

A red test that fails with "Cannot find module '@/actions/todos'" proves nothing about behavior, and ESLint
cannot even parse it. The skeleton gives every import a target whose body throws, so red means "the behavior is
missing", and `verify-red.sh` can distinguish that from a broken import. It also keeps the `feat(` commit a pure
behavior diff a reviewer can read against the spec.

### Why `verify-red.sh` uses "the commit before the tests" as the base

"Base branch" at the file level means "everything except the tests". In a PR that carries spec, skeleton, red and
green commits, `main` has none of the skeleton, so running the tests against `main` would fail on imports (the
wrong reason) for every feature. The parent of the first `test(FEAT-xxx)` commit is the exact state the
test-writer saw. `--range` and the CI `BASE_SHA`/`HEAD_SHA` pick which commits are searched.

## Watch-outs

- Stryker under pnpm cannot discover plugins through `node_modules` scanning; the explicit `plugins` list is
  required or it reports "no test runner".
- The TypeScript checker roughly doubles mutation time but stops type-invalid mutants from counting as survivors.
- `verify-red.sh` symlinks `node_modules` into the scratch worktree; a fresh clone must `pnpm install` first.
- AC ids are matched globally across `src/` and `e2e/`; keep ids unique per spec (they are) and never reuse a
  test title between features.
- `verify-red.sh` also caught a real slip in this lab: an infrastructure test (`errors.test.ts`) rode along in the
  red commit and was green at the base. Infrastructure tests go in the skeleton commit, never in `test(FEAT-xxx)`.
- A test commit that also fixes a stub (because the skeleton was wrong) is allowed by the guards (only `feat(`
  commits are checked) but defeats the purpose; amend the skeleton commit instead while the branch is unpushed.
- `it.todo` counts as neither pass nor fail; a red commit made only of todos fails `verify-red.sh` ("nothing executed").
