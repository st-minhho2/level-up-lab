# §15 Todos: an optional due date

Tier: full

- [ ] Lead approves spec (lead, <date>)

## Intent

A person who has a day by which an item must be done writes that day on the item, sees it in the item's row, changes
it when plans move, and removes it when it no longer matters. An item without a day looks exactly as it did before.
The day stays on the item after a reload. A due date is a note on the item: it never changes which item is shown
where, or whether it is done.

## Requirements (EARS)

| ID        | Pattern           | Requirement                                                                                                                                                                                                                                                                                                                             |
| --------- | ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| REQ-15.1  | Ubiquitous        | THE SYSTEM SHALL let each todo carry at most one due date, a calendar day (year, month, day) with no time of day and no time zone; a todo created as in §5 has none.                                                                                                                                                                    |
| REQ-15.2  | Event-driven      | WHEN a person submits a valid date for a listed todo THE SYSTEM SHALL store it as that todo's due date and show the text `Due <date>` in that todo's row, `<date>` written `YYYY-MM-DD` exactly as submitted.                                                                                                                           |
| REQ-15.3  | Event-driven      | WHEN a person submits an empty value for a listed todo THE SYSTEM SHALL store no due date for it and show no due-date text in its row.                                                                                                                                                                                                  |
| REQ-15.4  | Event-driven      | WHEN a due date is set, changed or cleared THE SYSTEM SHALL keep the todo's title and completion state, and keep every todo's position in the list (newest first, §5).                                                                                                                                                                  |
| REQ-15.5  | State-driven      | WHILE a todo has no due date THE SYSTEM SHALL show in its row no text other than what §5 and §6 show; every row, with or without a due date, holds one icon-only button named "Edit due date".                                                                                                                                          |
| REQ-15.6  | Event-driven      | WHEN a person activates "Edit due date" in a row THE SYSTEM SHALL show in that row one date field labelled "Due date", holding the todo's current due date (empty when none), and one button named "Update due date"; WHEN the update succeeds THE SYSTEM SHALL leave this edit mode.                                                   |
| REQ-15.7  | Unwanted behavior | IF the submitted value is neither empty nor a real calendar date written `YYYY-MM-DD` with a year from 0001 to 9999 THEN THE SYSTEM SHALL store nothing, report a field error on `dueDate` with the message `Due date must be a valid date`, and the row keeps the field open with the typed value.                                     |
| REQ-15.8  | Unwanted behavior | IF the submitted todo id does not exist THEN THE SYSTEM SHALL change nothing and report a field error on `id` (`Todo not found`, as in §5; no criterion; covered by the lib test, see below).                                                                                                                                           |
| REQ-15.9  | Ubiquitous        | THE SYSTEM SHALL keep the due date in PostgreSQL and refresh the page's list after a change, so that the list and a full page reload show the same due dates.                                                                                                                                                                           |
| REQ-15.10 | Unwanted behavior | IF setting or clearing a due date fails for any reason other than a missing todo id THEN THE SYSTEM SHALL change nothing, refresh nothing, report a field error on `form` with the §10 message, never a thrown error, write exactly one log entry as §11 specifies, named `setTodoDueDateAction`, and show the message in the same row. |
| REQ-15.11 | Event-driven      | WHEN the next attempt on the same row succeeds THE SYSTEM SHALL remove the message.                                                                                                                                                                                                                                                     |

A due date never changes list order (§1, §5): ordering stays creation time, newest first. Titles, completion and
order are those of §5; the failure message is the §10 text `Could not save, try again`, announced as an alert
(`role="alert"`); the log entry, its fields and its redaction are those of §11. The date is shown as written,
`YYYY-MM-DD`, in every browser and locale. Setting a date needs the database column of §3 and a migration
(`pnpm db:migrate --name add-todo-due-date`); existing rows get no due date.

## Function contracts

```ts
// src/lib/todo-due-date.ts (§15): pure; no Prisma, no server-only, so a client component may import it
export const DUE_DATE_INVALID_MESSAGE: 'Due date must be a valid date';
export const setTodoDueDateSchema: z.ZodObject<{ id: z.ZodString; dueDate: z.ZodType<string | undefined, string> }>; // id: min 1 'Todo id is required' (as toggleTodoSchema); dueDate: '' → undefined, else a real calendar date `YYYY-MM-DD`, year 0001-9999, no trimming, else DUE_DATE_INVALID_MESSAGE
export function dueDateToDate(dueDate: string): Date; // `${dueDate}T00:00:00.000Z`: the day as UTC midnight, so no time zone shifts it
export function dueDateOf(stored: Date | null): string | undefined; // stored.toISOString().slice(0, 10); null → undefined
// src/lib/todos.ts (§5 Todo, extended)
export interface Todo {
  readonly id: string;
  readonly title: string;
  readonly completed: boolean;
  readonly createdAt: Date;
  readonly dueDate?: string; // §15: 'YYYY-MM-DD'; absent when the todo has none
}
export function setTodoDueDate(id: string, dueDate: string | undefined): Promise<Todo>; // throws TodoNotFoundError; data: { dueDate } only (dueDateToDate(dueDate) or null); undefined clears
// listTodos, createTodo, toggleTodo, updateTodoTitle keep their signatures and now select and return dueDate through dueDateOf; createTodo stores none
// src/actions/todos.ts ('use server')
export function setTodoDueDateAction(id: string, dueDate: string): Promise<ActionResult<Todo>>; // Zod parse outside the try (fieldErrorsOf); one lib call; revalidatePath('/'); TodoNotFoundError → failure('id', 'Todo not found'); any other thrown value (lib or revalidatePath) → failure('form', MUTATION_FAILED_MESSAGE) after logMutationFailure('setTodoDueDateAction', error), nothing rethrown
// src/lib/logger.ts (§11): the union MutationActionName gains one member, 'setTodoDueDateAction'; no other change to §11
// src/components/todo-due-date.tsx ('use client')
export function TodoDueDate({
  todoId,
  dueDate,
}: {
  readonly todoId: string;
  readonly dueDate: string | undefined;
}): ReactNode; // one wrapper element: text `Due <dueDate>` when set; icon-only button aria-label "Edit due date"; in edit mode a <form> with a visually hidden <label> "Due date", <input type="date"> and the button "Update due date"; calls setTodoDueDateAction(todoId, draft) in a transition, the button disabled while pending; after a failed result <p role="alert"> with fieldErrors.dueDate?.[0] ?? fieldErrors.id?.[0] ?? fieldErrors.form?.[0] inside the wrapper; a successful result clears it and leaves edit mode
// src/components/todo-item.tsx: TodoItem({ todo }) renders <TodoDueDate todoId={todo.id} dueDate={todo.dueDate} /> inside its <li>; nothing else changes
// prisma/schema.prisma (§3): model Todo gains `dueDate DateTime? @db.Date`; migration `add-todo-due-date` adds one nullable column
```

Lib test for REQ-15.8 (no criterion): `setTodoDueDate('missing', …)` with `findUnique` resolving `null` rejects with
`TodoNotFoundError` and `update` is not called (asserted inside AC-15.2).

## Out of scope

Setting a due date while creating a todo (§5's form is unchanged), an overdue or due-soon highlight or any
comparison with today's date, sorting or grouping by due date (ordering stays creation time only, §1), filtering or
searching by due date, due times, time zones, recurring dates, reminders, a date range limit other than the format
(past dates are accepted), cancelling an edit (Escape/blur), a locale-formatted date, two tabs acting at once, undo.
