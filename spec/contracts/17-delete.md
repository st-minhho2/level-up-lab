# §19 Todos: delete a todo

Tier: full

- [ ] Lead approves spec (lead, <date>)

## Intent

A person who no longer wants one item removes just that item from the list, in one click on its row. Every other item
keeps its text, its state, its due date and its place, and the list stays the same after a reload. If the item cannot
be removed, the person is told right in its row and the item stays.

## Requirements (EARS)

| ID        | Pattern           | Requirement                                                                                                                                                                                                                                                                                                   |
| --------- | ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| REQ-19.1  | Event-driven      | WHEN a person activates the delete button of a listed todo THE SYSTEM SHALL delete that todo and no other.                                                                                                                                                                                                    |
| REQ-19.2  | Event-driven      | WHEN a todo is deleted THE SYSTEM SHALL keep every other todo's title, completion state and due date (§15), and keep the same relative order (newest first, §5).                                                                                                                                              |
| REQ-19.3  | Ubiquitous        | THE SYSTEM SHALL show, in every todo's row, in view mode and in edit mode (§6), exactly one icon-only button named "Delete todo", and it adds no text to the row.                                                                                                                                             |
| REQ-19.4  | Ubiquitous        | THE SYSTEM SHALL keep the result of a delete in PostgreSQL and refresh the page's list after it, so that the list and a full page reload show the same todos; WHILE no todo remains THE SYSTEM SHALL show "No todos yet" (§5).                                                                                |
| REQ-19.5  | Ubiquitous        | THE SYSTEM SHALL delete on a single activation of the button: there is no confirmation step and no undo.                                                                                                                                                                                                      |
| REQ-19.6  | State-driven      | WHILE a delete is pending THE SYSTEM SHALL keep that row's "Delete todo" button disabled, and enable it again once the delete has resolved.                                                                                                                                                                   |
| REQ-19.7  | Unwanted behavior | IF the submitted todo id is empty THEN THE SYSTEM SHALL delete nothing, refresh nothing, call no storage, and report a field error on `id` with the §5 message `Todo id is required`.                                                                                                                         |
| REQ-19.8  | Unwanted behavior | IF the submitted todo id names no todo (it never existed, or it was already deleted) THEN THE SYSTEM SHALL delete nothing, refresh nothing, write no log entry (§11, REQ-11.5), report a field error on `id` with the §5 message `Todo not found`, and show it in the same row.                               |
| REQ-19.9  | Unwanted behavior | IF deleting fails for any reason other than a missing todo id THEN THE SYSTEM SHALL delete nothing, refresh nothing, report a field error on `form` with the §10 message, never a thrown error, write exactly one log entry as §11 specifies, named `deleteTodoAction`, and show the message in the same row. |
| REQ-19.10 | Unwanted behavior | IF a delete fails as in REQ-19.8 or REQ-19.9 THEN THE SYSTEM SHALL show the message directly after the "Delete todo" button inside that row, keep the button usable, and keep the todo listed with the same title, state, due date and place.                                                                 |
| REQ-19.11 | Event-driven      | WHEN the next attempt on the same button succeeds THE SYSTEM SHALL remove the message.                                                                                                                                                                                                                        |

The id is validated by the existing `toggleTodoSchema` of §5 (a string of at least 1 character): the delete adds no
Zod schema and no message of its own. The failure message is the §10 text `Could not save, try again`, announced as
an alert (`role="alert"`); the log entry, its fields and its redaction are those of §11. A missing id is not a
failure in the sense of §10 (as for toggle and edit): it is not logged, and nothing is refreshed, so the row stays
with the message `Todo not found`. A delete is final in one step: the todo cannot be restored. Titles, duplicates,
completion and order are those of §5.

## Function contracts

```ts
// src/lib/todo-delete.ts (§19); Prisma only through '@/lib/prisma'
export function deleteTodo(id: string): Promise<void>; // one deleteMany({ where: { id } }); count 0 → throws TodoNotFoundError (from '@/lib/todos', §5); no other prisma.todo call
// src/actions/delete-todo.ts ('use server')
export function deleteTodoAction(id: string): Promise<ActionResult<{ id: string }>>; // toggleTodoSchema.safeParse({ id }) outside the try (a failure resolves { ok: false, fieldErrors: fieldErrorsOf(error) }, lib not called); one lib call, then revalidatePath('/'); TodoNotFoundError → failure('id', 'Todo not found') with no log and no revalidate; any other thrown value (lib or revalidatePath) → failure('form', MUTATION_FAILED_MESSAGE) after logMutationFailure('deleteTodoAction', error), nothing rethrown; success → { ok: true, data: { id } }
// src/lib/logger.ts (§11): the union MutationActionName gains one member, 'deleteTodoAction'; no other change to §11
// src/components/delete-todo-button.tsx ('use client')
export function DeleteTodoButton({ todoId }: { readonly todoId: string }): ReactNode; // one wrapper element holding an icon-only <button type="button"> with aria-label "Delete todo" (and title "Delete todo") and no visible text; calls deleteTodoAction(todoId) in a transition; disabled while pending; after a failed result <p role="alert"> (or a span) with fieldErrors.id?.[0] ?? fieldErrors.form?.[0] as the button's next sibling inside the wrapper; a successful result clears it
// src/components/todo-item.tsx: TodoItem({ todo }) renders <DeleteTodoButton todoId={todo.id} /> inside its <li>, in view mode and in edit mode; nothing else changes (its own single role="alert" span of §10 stays)
// src/app/page.tsx, src/lib/todos.ts, src/actions/todos.ts, src/components/todo-due-date.tsx, src/components/todo-form.tsx: unchanged
```

Lib test for the real storage call (no extra criterion): AC-19.1 asserts the exact `deleteMany` argument, so no
`findUnique` or `delete` is used and a missing id cannot be told apart from a deleted one by a second query.

Test note for `src/components/todo-item.test.tsx` (an existing file): `TodoItem` now imports
`@/actions/delete-todo`, so that file mocks the module at the boundary (`vi.hoisted` object, `vi.mock`), as it does
`@/actions/todos`; its existing tests are not changed otherwise.

## Out of scope

A confirmation dialog or prompt, undo or restore, soft delete or a trash view, a count or message of how many were
deleted, deleting several selected todos (§9 clears completed ones), keyboard shortcuts, an animation, optimistic UI,
removing a stale row after "Todo not found" (the row keeps its message, as for toggle), a "Todo not found" refresh,
deleting from two tabs at once, any change to the page layout outside the row (§7).
