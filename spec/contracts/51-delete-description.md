# §53 Todos: a failed delete's message describes the "Delete todo" button

Tier: full

- [ ] Lead approves spec

## Intent

A person who uses a screen reader and activates a row's "Delete todo" button hears the failure as it appears (§10, an
alert), but when they come back to the button later the message is not tied to it: the button reads only its name,
and they cannot tell which button failed. After this section, as long as a failed delete's message is shown, the
button carries that message as its description, so a screen reader reads the name "Delete todo" and then the message.
The message, its place and the name do not change, and a button with no message shown has no description of this kind.

## Requirements (EARS)

| ID       | Pattern           | Requirement                                                                                                                                                                                                                                                                                                                                                                                                      |
| -------- | ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| REQ-53.1 | State-driven      | WHILE a failed delete's message (`Could not save, try again` or `Todo not found`, §19 REQ-19.10) is shown in a row, THE SYSTEM SHALL give that row's "Delete todo" button an `aria-describedby` attribute whose value is the `id` of the element that holds the message, so that the button's accessible description is exactly the message text and follows the message when a later failure shows another one. |
| REQ-53.2 | Ubiquitous        | THE SYSTEM SHALL make that `id` unique among the elements of the page and independent of the todo's id: it is generated once per button instance, so it never equals `todo-<id>-error` (§10), `todo-<id>-due-date-error` (§15) or the id generated for another row's button.                                                                                                                                     |
| REQ-53.3 | State-driven      | WHILE no failed delete's message is shown THE SYSTEM SHALL give the button no `aria-describedby` attribute.                                                                                                                                                                                                                                                                                                      |
| REQ-53.4 | Event-driven      | WHEN a delete succeeds THE SYSTEM SHALL remove the message and the `aria-describedby` attribute together (the row itself is removed by the refresh of §19 REQ-19.4).                                                                                                                                                                                                                                             |
| REQ-53.5 | State-driven      | WHILE a retry after a failed delete is pending (§19 REQ-19.6, from the confirmation on) THE SYSTEM SHALL keep the message and the `aria-describedby` attribute of the earlier failure, and replace or remove them only when the retry resolves.                                                                                                                                                                  |
| REQ-53.6 | Unwanted behavior | IF the confirmation of §35 is cancelled while a failed delete's message is shown THEN THE SYSTEM SHALL keep the same message element, the `aria-describedby` attribute and the description exactly as they were (§35 REQ-35.3).                                                                                                                                                                                  |
| REQ-53.7 | Ubiquitous        | THE SYSTEM SHALL change nothing but that attribute and the `id` on the message element: the button's name stays "Delete todo" (`aria-label` and `title`), the message keeps `role="alert"`, its text and its place as the button's next sibling in the same wrapper (§19 REQ-19.10), and the button gets no other `aria-*` attribute.                                                                            |

A delete that fails shows its message in the delete button's own wrapper, apart from the row's toggle message
(§10, `todo-<id>-error`): a row may show both at once, and each describes only its own control. The message text,
the failure results, the confirmation, the pending state and the log entry are those of §19, §10 and §35.

Edits to other sections that this one makes: §35 REQ-35.5 says the rule covers the confirmation only and that §53 adds
`aria-describedby` for the failure message. The comment of §35's function contract ("no prop, state, element or
attribute is added") describes the confirmation and does not apply to §53, for the same reason: the component is
`src/components/delete-todo-button.tsx`. No other line of any contract changes, and no requirement or criterion is
lifted. §19 REQ-19.3 and §20 REQ-20.7 hold: no text, `role`, `aria-label` or control is added to the row.

## Function contracts

```ts
// src/components/delete-todo-button.tsx ('use client'; §19, §35, extended)
export function DeleteTodoButton({ todoId }: { readonly todoId: string }): ReactNode; // signature unchanged; `const messageId = useId()` once per instance; the message element (role="alert") gets id={messageId}; the button gets aria-describedby={error !== undefined ? messageId : undefined}; `error` is set and cleared exactly as in §19 (set on settle, kept while pending, cleared by the next success); no other prop, state or element is added
```

The only file of `src/` this section changes is `src/components/delete-todo-button.tsx`. No new export, Server Action,
Zod schema, Prisma model, route, lib function or environment variable; `src/components/todo-item.tsx`,
`src/actions/delete-todo.ts` and `src/lib/*` keep their contracts.

How the criteria observe it: AC-53.1 to AC-53.6 are component tests with Testing Library in
`src/components/delete-todo-button-description.test.tsx` (`deleteTodoAction` and, for AC-53.6, the §5, §6 and §15
actions mocked with `vi.hoisted` as `delete-todo-button.test.tsx` and `todo-item.test.tsx` do; `window.confirm`
stubbed as §35 says); descriptions are read with `toHaveAccessibleDescription`. The idle description is not asserted:
`title="Delete todo"` may supply one, so REQ-53.3 is checked on the absence of the attribute. A failing delete is not
reproduced in the browser, so there is no e2e criterion. The sections are numbered by feature order and the contract
files by file order, so §53 lives in `51-delete-description.md`.

## Out of scope

Announcing the message differently (`aria-live`, `aria-atomic`, a status role), a visible change to the row or the
message, a new message text, moving focus to the message or the button, removing the title attribute, describing any
other control (the checkbox, "Edit title", the due-date controls keep their own messages of §10 and §15),
`aria-errormessage` or `aria-invalid`, a message that is cleared by a cancelled confirmation or by a timer, a stale
row removed after "Todo not found" (§19), any change to the log entry or to the failure results.
