# §44 Todos: after a successful add, focus is in the "New todo" box

Tier: full

- [ ] Lead approves spec

## Intent

A person who adds a todo usually adds the next one. Today the click on "Add" leaves focus on the button, the button is
disabled while the save is pending, and focus then falls to the page, so a second title needs a click or a Tab
before the first useful key. After this section a saved todo leaves the cursor in the empty "New todo" box, ready for
the next title. Nothing else about adding changes, and a page that has only loaded, or a save that failed, moves
focus nowhere.

## Requirements (EARS)

| ID       | Pattern           | Requirement                                                                                                                                                                                                                                                                                                                                                                                                 |
| -------- | ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| REQ-44.1 | Event-driven      | WHEN `createTodoAction` resolves `{ ok: true, … }` for the form of §7 THE SYSTEM SHALL, once the box holds the empty value of §5 REQ-5.2 and §10, make the "New todo" box `document.activeElement`, whichever control had focus before (the "Add" button, the box, or none).                                                                                                                                |
| REQ-44.2 | Unwanted behavior | IF the form renders for the first time (server render, hydration, mount) or re-renders for a reason other than a new settled result of `createTodoAction` (a key typed, a save pending, the counter or the §39 warning shown or removed) THEN THE SYSTEM SHALL NOT focus a control: `document.activeElement` is what it was, so on load it is `document.body` and the `/` shortcut (§25) types into no box. |
| REQ-44.3 | Unwanted behavior | IF `createTodoAction` resolves `{ ok: false, … }` (a `title` field error of §5 REQ-5.3 or a `form` failure of §10) THEN THE SYSTEM SHALL NOT focus the box: no `focus()` call is made on it and the box keeps its value (§10).                                                                                                                                                                              |
| REQ-44.4 | Ubiquitous        | THE SYSTEM SHALL focus the box once for each successful result: a person who moves focus elsewhere after the save keeps it there until the next successful result, and two successful results in a row focus the box twice.                                                                                                                                                                                 |
| REQ-44.5 | Ubiquitous        | THE SYSTEM SHALL change nothing but focus: the box's value, `name`, `id`, `maxlength`, `aria-describedby`, accessible name "New todo", the counter (§18), the warning (§39), Escape (§29), the single `role="alert"` message of §5 and §10, the data submitted and the request count are those of §5, §7, §10, §18, §29 and §39; the box is empty, so no text is selected.                                  |

## Function contracts

```ts
// src/components/todo-form.tsx (§5, §7, §10, §18, §29, §39, extended; already 'use client'; no new component, props unchanged)
export function TodoForm(): ReactNode; // as before, plus: each time the `state` of useActionState(createTodoAction, null) becomes a new result with ok === true, after the commit that settles the action (so after React's form reset) the box, through the existing `box` ref, receives focus() once; state null (first render) and a result with ok === false never call focus(); a re-render with the same `state` does not
```

The only file of `src/` this section changes is `src/components/todo-form.tsx`. No new export, Server Action, Zod
schema, Prisma model, query, environment variable, prop or lib function. `src/app/page.tsx`,
`src/actions/todos.ts`, `src/lib/*` (including `title-count.ts` and `escape-search.ts`) and every other component keep
their contracts.

How the criteria observe it: jsdom supports `focus()` and `document.activeElement` on a text `input`, so AC-44.1 to
AC-44.5 are component tests with Testing Library in `src/components/todo-form-focus.test.tsx` (`createTodoAction`
mocked with `vi.hoisted` at `@/actions/todos`, as `todo-form.test.tsx` does); AC-44.6 and AC-44.7 are Playwright
tests in `e2e/44-new-todo-focus.spec.ts` that read focus with `toBeFocused`. The sections are numbered by feature
order and the contract files by file order, so §44 lives in `42-new-todo-focus.md`.

## Out of scope

Focusing the box after a failed save, on load or on a reload, after Escape (§29), after a toggle, edit, delete or
"Mark all complete", or when the list changes for any other reason; restoring focus to the "Add" button; scrolling the
new row into view; announcing the focus move to assistive technology; moving focus in the search box, the title
editor or the due-date editor; a visible focus style of our own; a keyboard shortcut for the box.
