## Open questions

1. **Does the typed title survive a failed create?** Evidence: React 19 resets an uncontrolled `<form action={fn}>` when its action finishes, whatever the result. I ran a throwaway probe (jsdom 30 + `react-dom` 19.1.0 from this worktree, outside the repo, nothing committed): an uncontrolled `<input name="title">` typed with `Buy milk` and a `useActionState` form whose action resolves (a) `{ ok: true }`, (b) `{ ok: false, fieldErrors: { title: [...] } }`, (c) `{ ok: false, fieldErrors: { form: [...] } }` ends with value `''` in all three, the alert text correctly shown in (b) and (c). So today a §5 validation error already empties the box; it costs nothing only because the one reachable title error is a blank title (`maxLength={200}` blocks the 201-character case). No existing test pins the box content on an error: `todo-form.test.tsx` "AC-5.3: shows the title field error returned by the action" asserts only the message, and "AC-5.2: submits the typed title and clears the box on success" asserts `''` after success. After B1.5, a database failure with a real title would empty the box under "Could not save, try again", while the edit row (REQ-10.3) keeps its draft.

   Proposed decision: **B**. Why: §10's intent is "click again without reloading"; the edit row already keeps its draft (REQ-10.3); losing a typed title to a database hiccup is the one cost the message cannot undo. What changes otherwise: if the lead rules A, delete in §10 the Intent sentence "What they typed is still in the box", REQ-10.6's "keep the typed title in the box", AC-10.5's `value Buy milk` assertion (and its `''` after the second click, which stays true), and the `todo-form.tsx` draft sentence in Function contracts; if C, the Out of scope line about the box after a `title` error goes and §5 needs a sentence. The decision is one the lead takes when ticking the box (D-7); no new D-n is needed (see Needs a ruling).

3. **Box content after a `title` error (§5).** Proposed: out of scope, behavior as today (the box is emptied by React's reset; only a blank title can reach it). Why: no section or test pins it, and option B needs it kept as is. What changes otherwise: see option C.

4. **Test layer.** Proposed: unit and component only, as for B1.4. `AC-10.4` in `src/actions/todos.test.ts` (mocks: `@/lib/todos` rejecting, `next/cache`); `AC-10.5` in `src/components/todo-form.test.tsx` (mock `@/actions/todos`, `vi.hoisted`). jsdom reproduces React's form reset (probe above), so the "keeps `Buy milk`" assertion is meaningful, not vacuous. No e2e: a real create cannot be made to fail mid-test without a fault-injection hook, which is a configuration change to ask about first (same as B1.4). What changes otherwise: an e2e needs that hook.

5. **One alert, several results in a row.** Proposed: the alert slot is the single `<p role="alert">`; each new result replaces its text, so a `form` failure followed by a `title` error shows exactly 1 alert (the title text) and a failure followed by a failure still shows 1. Why: it follows from `useActionState` replacing the state; AC-10.5 asserts "exactly 1" only for the failure and the recovery. What changes otherwise: a second slot (a REQ and a criterion).

6. **Message wording and logging.** Not re-asked: D-11 fixes the text `Could not save, try again` for every control and says the swallowed error is not logged until a logger card lands.
