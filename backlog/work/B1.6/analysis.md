3. **Log level and an environment switch?** (the brief's (c)). Proposed: none. No new §4 key, no `NODE_ENV` branch, `level` is the constant `error`. Why: invariant 5 lists port, schema, build dir, storage and cache prefix; a standard stream is none of these, and a key would change AC-4.1 ("applies every default") and the `.env.example` rewrite in `scripts/worktree.sh`. One call site has no need for `info` or `debug`. Under `NODE_ENV=test` the line is written like anywhere else; the red commit keeps the output out of the test run (question 4). 4. **Test noise and where tests observe the logger.** Proposed: action tests add `vi.mock('@/lib/logger', …)` with a `vi.hoisted` spy (testing.md: mocks at module boundaries; adding a mock is allowed) in the red commit, which also silences the four existing "db down" failure tests; `src/lib/logger.test.ts` spies on `process.stderr.write` and `process.stdout.write`, mocks `@/lib/env`, uses fake timers for `time`. No test spies on `console` (the lint override does not cover tests). Why: the writes would otherwise print 4 JSON lines into every `pnpm test` run. What changes otherwise: without the mock the existing tests still pass but print; a `NODE_ENV=test` silence branch would add an untested branch to the logger and contradict AC-11.1's "one chunk".

5. **The numbers 500 and 2000 (message and stack caps), and keeping the stack.** Proposed: as in REQ-11.4. Why: they are not in any existing section or D-n, so they are `[estimate]`s: Node keeps 10 stack frames by default (a stack of roughly 1 to 2 KB); 500 holds one Prisma header line plus its reason; the whole line stays near 3 KB, under the 4096 bytes after which writes to a pipe may interleave on POSIX [unverified for the deployment target]. A multi-byte message can exceed that, which is accepted. What changes otherwise: edit the two numbers in REQ-11.4, AC-11.3 and the constants; dropping the stack removes `stack` from REQ-11.3, AC-11.1, AC-11.2 and the cap.

6. **Extra fields (`todoId`, input, request id).** Proposed: none; the signature is `(action, error)`. Why: the card asks "which action"; the id is not secret but every field is one more criterion, and input is the leak vector. What changes otherwise: `logMutationFailure(action, error, context?)` with `context: { todoId?: string }`, one REQ and one AC (a 7th criterion, still allowed).

7. **Function and file names.** Proposed: `src/lib/logger.ts` exporting `logMutationFailure` and the `MutationActionName` union, narrow on purpose. Why: a generic `logError(event, fields)` invites passing input; the union makes a misspelled action name a type error. What changes otherwise: a generic logger needs a field allow-list requirement.

## Needs a ruling

Yes, one record, **blocking only if the lead rejects option A or wants R3**: the choice of sink and of what a log may contain is a policy the human owns (invariant 7, "Ask before any dependency, tool, CI, hook or configuration change"), and D-11's sentence "the swallowed error is not logged until a logger card lands" needs its successor.

Proposed D-12 text: "Swallowed mutation failures (§11) are logged by an in-repo logger, `src/lib/logger.ts`, as one JSON line on the standard error stream; `console` stays banned in `src/`, and no logging dependency and no log-level environment key are added. An entry carries the action's name and the error's name, message, string code and stack, with the `DATABASE_URL` value and its password replaced by `[redacted]`, and never the person's input. This replaces the sentence in D-11 that the swallowed error is not logged."

If the lead accepts A and R2 by ticking the approval box under §11's heading (D-7), the record is a formality for `dev-lead` to append; options B and C each need a human act before the `feat` commit (label, or a dependency approval) and change §11's Function contracts first.
