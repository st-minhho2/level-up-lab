## Open questions

1. Where does a rejected action turn into a message? · Proposed: the Server Actions never reject for an expected failure: each catches every error that is not `TodoNotFoundError` and returns `failure('form', MUTATION_FAILED_MESSAGE)` (`'Could not save, try again'`), without calling `revalidatePath`; the components read `fieldErrors.form?.[0]` into the alert they already have (a new `<p role="alert">` for the clear button). It reuses §7's own rule and the `ActionResult` shape, and `fieldErrorsOf` already uses `form` · otherwise each component wraps `await …Action()` in `try/catch`, the contract "errors travel as data" keeps a hole, and the action tests prove nothing about the failure.
2. Does `createTodoAction` / `TodoForm` join? · Proposed: no, out of scope in §10, follow-up card (B1.5) · the card names three controls; the create path has no `try/catch` either and would reject to the error boundary; including it makes a fourth behavior (`full` tier) and a form-level message slot in `TodoForm` · if the lead wants §7's "never throw" to hold for every action in one change, widen §10 to `full` and add a fourth criterion for the form.
3. A request that fails before the action runs (network down, server unreachable) still rejects the client promise and reaches the error boundary · Proposed: out of scope; the card's intent is a database failure mid-click · catching it needs a `try/catch` in each component, i.e. a second mechanism with its own criteria · if wanted, §10 gains a REQ and the components catch the rejection and show the same message.
4. Message wording: one text, `Could not save, try again`, for toggle, save and clear · Proposed: keep one (card text allowed "or similar"); a delete reads slightly off ("save") but the lead can rule a different wording before approving the box · per-control texts need three constants and three assertions · if changed, only the constant and the Then cells of AC-10.1 to AC-10.3 change.
5. Test layer for "list unchanged" and "no error boundary" · Proposed: unit and component tests only. AC-10.1 asserts no `revalidatePath` and a resolved (not rejected) promise; AC-10.2 and AC-10.3 assert the checkbox, the draft and the button state. No e2e: failing a real mutation needs the database stopped mid-test, which `e2e/` has no mechanism for · a mocked lib cannot show the rendered page staying put · if the lead wants an e2e, it needs a fault-injection hook, which is a code and configuration change to ask about first.
6. The literal `'Could not update the todo'` in `todo-item.tsx` · Proposed: delete it (REQ and function contract say so): after §10 an `ok: false` result always carries `id`, `title` or `form` · keeping it leaves an unreachable branch (a surviving mutant for `pnpm test:mutation`, ≥ 70 % on `src/actions` + `src/lib`; components are not in the mutation scope, so this is hygiene) · if kept, §10 must name when it shows.
7. Logging the cause · Proposed: none; `console` is banned in `src/` (`ts-style.md`) and the repo has no logger, so the swallowed `Error` leaves no trace anywhere server-side · a failure that is invisible to the operator is a real cost, listed here so it is a choice · if wanted, a logger is a dependency or a new module and a separate card.
8. Message disappears when · Proposed (REQ-10.5): on the next successful attempt of the same control; the existing `TodoItem` does this already (`setError(undefined)`), `ClearCompletedButton` is new · no timer, no dismiss button · if a dismiss control is wanted it is another criterion.
9. Housekeeping outside this role's write set, for `dev-lead`: (a) `backlog/README.md` row B1.4 still reads "— (section to write)" in the Spec § column and "Spec: change:"-era text; (b) `spec/features-map.md` has no F8 row (add at `docs(map): F8 … [B1.4]` when code lands: `src/actions/todos.ts`, `src/lib/action-result.ts`, `src/components/todo-item.tsx`, `src/components/clear-completed-button.tsx`; `src/actions/CLAUDE.md` says "only unexpected errors are rethrown" and `src/components/CLAUDE.md` names the alert contract, both drift once this lands); (c) `src/actions/todos.ts` header comment says "no failure arm" for §9 · none changes behavior.

## Needs a ruling

Yes, one, flagged for the human: **does §10 need a D-n because it changes the "other errors rethrown" arms of §5/§6/§9?**

- §5 and §6 (their text): silent on the rethrow arm. The rethrow exists only in `src/actions/todos.ts` (`throw error`), in `src/actions/CLAUDE.md` ("only unexpected errors are rethrown") and in two tests, both titled "rethrows a non-TodoNotFoundError from the lib (review: instanceof arm)" (`src/actions/todos.test.ts`, one in the toggle block, one in the edit block). §7 says "Actions return errors as data, never throw them to the client", so for §5/§6 this is code catching up with §7; no D-n is needed for the section text.
- §9 (its text): the function-contract line for `clearCompletedTodosAction` ends "the failure arm is never returned" and the `ClearCompletedButton` comment says the result is ignored. §10 reverses both. `spec/CLAUDE.md` and §8 ("a change that alters an existing section's behavior … needs a D-n") make that a D-n, followed by a `docs(spec): §9 …` edit of that one clause before any test. I may not edit §9, so §10 states the new rule and leaves the clause for the lead.
- Existing tests: the two "rethrows …" tests assert the behavior §10 replaces, so they cannot stay green. `testing.md` forbids loosening a test and says "change the spec first"; the clean path is: ruling, `docs(spec)` for §9, then the card's `test(…) (red)` commit rewrites those two tests (to the `AC-10.1` assertions) and adds the new ones. Nothing in the `feat(…)` commit may touch them (`check-feat-commits.sh`).

Decision request (advisor's shape):

```
Context:     §10 (card B1.4) makes toggle, edit-save and clear-completed return { ok: false, fieldErrors: { form: ['Could not save, try again'] } }
             instead of rethrowing a non-TodoNotFoundError. §7 already says actions never throw to the client; §9's contract line says
             "the failure arm is never returned"; two action tests pin the rethrow.
Options:
  A  Rule that §10 governs: actions never reject for an expected failure.
     Behavior: a database error shows the message beside the control, list unchanged.   Cost: one `docs(spec): §9` clause edit, two tests rewritten in the red commit.
     Risk: the swallowed error is not logged anywhere (no logger).                      Reversible: yes (restore the rethrow arm by a later D-n).
  B  Keep the rethrow, catch in each component (try/catch around the awaited action).
     Behavior: same UI.   Cost: three try/catch blocks, the action layer still throws, §7's rule stays violated.
     Risk: a new component that forgets the catch reintroduces the error boundary.      Reversible: yes.
Recommended: A, flips if the lead wants server Actions to stay throwing for observability (an error boundary or a reporter reads the error): then B plus a logger card.
Affects:     §9 (one clause), §10 (AC-10.1 .. AC-10.3), src/actions/todos.ts, src/actions/CLAUDE.md, the two "rethrows …" tests, cards B1.4 (and B1.5 for the create path).
```

Proposed D-n text if A is ruled: "Server Actions never reject for an expected failure: any error other than `TodoNotFoundError` becomes `{ ok: false, fieldErrors: { form: ['Could not save, try again'] } }` (§10); this supersedes the 'failure arm is never returned' clause of §9."
